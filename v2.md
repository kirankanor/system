# V2 Specification — Production-Grade RAG Ingestion Pipeline

## 1. Objective

Upgrade the existing RAG Code Library to V2 by implementing a complete, production-oriented document ingestion pipeline.

The pipeline must process documents from source discovery through extraction, normalization, chunking, embedding, indexing, verification, failure recovery, security, and lifecycle management.

**Do not rebuild components that already exist and satisfy the requirements.** First inspect the repository, compare the existing implementation against all 20 steps below, identify gaps, and then implement only missing or incomplete functionality.

The objective is to integrate these capabilities into the existing architecture while preserving backward compatibility where practical.

## 2. Mandatory workflow

Before modifying code:

1. Inspect the complete repository structure, source code, manifests, configuration, tests, dependency declarations, and documentation.
2. Identify existing implementations for each of the 20 steps.
3. Classify each step as:
   - **Complete:** implementation and acceptance tests satisfy the requirements.
   - **Partial:** implementation exists but has missing behavior, edge cases, or tests.
   - **Missing:** no suitable implementation exists.
   - **Blocked:** a required external service, unresolved interface, or product decision prevents verification.
4. Produce a gap analysis mapping each requirement to existing files, missing files, dependencies, and tests.
5. Identify shared infrastructure that should be reused rather than duplicated.
6. Define the implementation plan and task dependencies.
7. Implement the approved V2 scope, concentrating on missing and partial functionality.
8. Run the available tests, add regression tests, and update documentation.

Do not mark functionality complete merely because a class, function, interface, or placeholder exists. Verify its actual behavior.

Do not replace working implementations unnecessarily. Avoid unrelated refactoring and preserve the existing public API unless a change is necessary and documented.

## 3. The 20 required ingestion steps

### Step 1 — Document Discovery

**Purpose:** Discover documents from configured sources.

**Required capabilities:**
- Discover files in a specified directory, recursively or non-recursively.
- Support configurable file extensions and exclusion patterns.
- Support multiple discovery sources through explicit adapters, where applicable.
- Detect newly added, modified, and deleted documents.
- Return structured discovery records containing source location and relevant file metadata.
- Support deterministic output ordering when requested.

**Important behavior:**
- Handle Unicode filenames, inaccessible directories, empty folders, and duplicate paths.
- Do not follow symlinks or junctions outside the authorized root.
- Do not assume every discovered file is supported.
- Separate discovery from document parsing.
- Do not claim cloud storage or URL discovery is implemented unless the corresponding adapter exists and works.

**Acceptance criteria:**
- Tests cover nested directories, exclusions, unsupported extensions, inaccessible paths, and duplicate discovery.
- Discovery does not read or modify document contents unnecessarily.
- Results are reproducible under equivalent inputs.

### Step 2 — File Validation

**Purpose:** Determine whether a discovered file is safe and eligible for ingestion.

**Required capabilities:**
- Validate supported file types using appropriate file identification.
- Enforce configurable file-size limits.
- Detect empty, corrupt, unsupported, and malformed files.
- Validate relevant format-specific constraints.
- Produce structured validation results with actionable errors.

**Important behavior:**
- Do not trust file extensions alone.
- Treat MIME type and magic-byte detection as signals, not absolute proof of safety.
- Reject files that exceed configured limits before expensive processing.
- Do not execute embedded scripts, macros, or document content.
- Distinguish rejected files from transient validation failures.

**Acceptance criteria:**
- Tests cover renamed files, corrupt documents, empty files, oversized files, unsupported formats, and malformed inputs.
- Rejected files do not proceed into extraction.
- Failure reasons are recorded without exposing sensitive content.

### Step 3 — Document Identification

**Purpose:** Generate stable document identities and detect duplicate content.

**Required capabilities:**
- Generate a stable document identifier.
- Calculate a cryptographic content hash.
- Distinguish source identity from content identity.
- Detect duplicate documents with identical content, even when filenames differ.
- Record document versions or content revisions.

**Important behavior:**
- Do not use filenames alone as unique identifiers.
- Define how renames, moves, content changes, and duplicate sources affect identity.
- Do not overwrite a newer document version with an older version.
- Make hashing deterministic.
- Do not assume identical content always means identical source provenance.

**Acceptance criteria:**
- Identical content produces identical content hashes.
- Changed content is detected.
- Renamed files follow the documented identity policy.
- Duplicate detection preserves the provenance of each source.

### Step 4 — Document Loading

**Purpose:** Select and invoke the appropriate parser for each supported document format.

**Required capabilities:**
- Provide a common loader interface.
- Support the formats required by the existing project, such as PDF, DOCX, HTML, Markdown, and plain text.
- Allow format-specific loader adapters.
- Support OCR as an optional fallback for scanned documents.
- Return structured extraction results with source metadata.

**Important behavior:**
- Keep format-specific dependencies optional.
- Report unsupported formats explicitly.
- Handle encrypted, malformed, empty, and partially readable documents.
- Avoid loading entire large documents into memory when streaming or incremental processing is feasible.
- Do not silently substitute an incompatible parser.

**Acceptance criteria:**
- Each supported format has representative tests and documented dependencies.
- Missing optional dependencies produce actionable errors.
- Parser selection and fallback behavior are deterministic and testable.

### Step 5 — Text Extraction

**Purpose:** Extract useful text and structural information from loaded documents.

**Required capabilities:**
- Extract text from supported documents.
- Preserve page numbers, section headings, and other available structural information.
- Represent tables, lists, and document sections where supported.
- Preserve source locations so downstream citations can identify the original content.
- Support OCR results for scanned pages when configured.

**Important behavior:**
- Preserve reading order as accurately as the parser allows.
- Handle documents containing both selectable text and scanned images.
- Record extraction warnings and page-level failures.
- Do not invent missing text or claim perfect structural extraction.
- Distinguish a successfully extracted empty page from a failed extraction.

**Acceptance criteria:**
- Tests verify extracted text, source metadata, page mapping, and partial failures.
- Extraction results can be traced to their original documents.
- Unsupported structural features are documented.

### Step 6 — Text Normalization

**Purpose:** Normalize extracted text before metadata enrichment and chunking.

**Required capabilities:**
- Handle Unicode normalization and common encoding issues.
- Normalize whitespace and line endings.
- Remove configurable extraction artifacts.
- Normalize repeated headers or footers when safely identifiable.
- Preserve meaningful punctuation, headings, tables, code, and formatting.

**Important behavior:**
- Do not aggressively normalize content in ways that change meaning.
- Preserve the original extracted text or sufficient provenance to reconstruct the transformation history.
- Make normalization rules configurable where appropriate.
- Make normalization idempotent where the selected transformations permit it.
- Report transformations that materially alter the content.

**Acceptance criteria:**
- Tests cover Unicode, whitespace, repeated page artifacts, code, tables, and multilingual text.
- Normalization does not silently remove meaningful content.
- The same input and configuration produce the same output.

### Step 7 — Metadata Enrichment

**Purpose:** Attach consistent metadata to documents and extracted content.

**Required metadata, where available:**
- Document ID and content hash.
- Source location and source type.
- Original filename and detected format.
- Page number, section, and extraction location.
- Ingestion timestamp and document version.
- Parser identity and relevant processing configuration.
- Custom source metadata.

**Important behavior:**
- Distinguish extracted metadata from system-generated metadata.
- Preserve original metadata and provenance.
- Handle missing, malformed, and conflicting values.
- Define precedence rules for metadata collisions.
- Do not invent authors, dates, titles, or source information.
- Prevent untrusted document metadata from overriding protected system fields.

**Acceptance criteria:**
- Metadata follows a documented schema.
- Required fields are validated.
- Metadata survives chunking and indexing where required.
- Invalid metadata generates clear validation errors.

### Step 8 — Chunking

**Purpose:** Divide extracted documents into retrieval-sized chunks while preserving useful context.

**Required capabilities:**
- Support the existing chunking strategies, such as fixed-size, recursive, sentence-aware, token-aware, Markdown-header-aware, and semantic chunking where implemented.
- Configure chunk size and overlap.
- Preserve document IDs, source locations, and relevant metadata.
- Generate stable chunk identifiers.
- Support parent-child relationships or structure-aware chunks where needed.

**Important behavior:**
- Enforce chunk-size limits according to the selected strategy.
- Define how oversized sentences, tables, sections, and code blocks are handled.
- Avoid empty chunks and unnecessary duplication.
- Preserve source offsets or equivalent citation locations when supported.
- Do not assume character count equals token count.
- Keep strategy-specific dependencies optional.

**Acceptance criteria:**
- Each supported strategy has tests for normal and boundary inputs.
- Chunks can be traced back to their original source.
- Chunk identifiers and metadata remain consistent for unchanged inputs under the same configuration.

### Step 9 — Chunk Validation

**Purpose:** Validate chunks before deduplication, embedding, or indexing.

**Required checks:**
- Empty or whitespace-only chunks.
- Configurable minimum and maximum size.
- Required metadata.
- Missing document references.
- Invalid chunk IDs.
- Invalid source locations.
- Extraction anomalies and malformed structural data.

**Important behavior:**
- Distinguish warnings from fatal validation errors.
- Do not silently discard useful chunks.
- Allow explicit policies for rejecting, repairing, or quarantining invalid chunks.
- Record why a chunk failed validation.

**Acceptance criteria:**
- Invalid chunks cannot reach embedding or indexing without an explicitly documented exception.
- Tests cover each validation rule.
- Validation results are observable and attributable to the source document.

### Step 10 — Chunk Deduplication

**Purpose:** Detect duplicate chunks and prevent unnecessary embedding and indexing work.

**Required capabilities:**
- Calculate deterministic chunk content hashes.
- Detect exact duplicates.
- Optionally support configurable near-duplicate detection.
- Reuse existing embeddings when the chunk and embedding configuration are compatible.
- Preserve document provenance for shared content.

**Important behavior:**
- Distinguish exact duplicates from semantically similar content.
- Do not remove overlapping passages merely because they share common text.
- Avoid merging chunks from different sources in ways that destroy attribution.
- Define whether deduplication occurs within one document, across documents, or both.
- Never reuse embeddings across incompatible embedding models or configurations.

**Acceptance criteria:**
- Identical chunks can be recognized reliably.
- Deduplication respects the selected scope.
- Source provenance remains available.
- Tests verify that changed content and incompatible embeddings are not incorrectly reused.

### Step 11 — Embedding

**Purpose:** Convert validated chunks into vectors suitable for semantic retrieval.

**Required capabilities:**
- Use the existing embedding interface or protocol.
- Support configurable embedding providers.
- Batch requests where supported.
- Track model identity, dimensions, and relevant configuration.
- Handle temporary provider failures and rate limits.
- Reuse compatible cached embeddings when available.

**Important behavior:**
- Preserve the mapping between chunks and returned vectors.
- Validate vector dimensions, numerical validity, and expected output shape.
- Never silently omit failed chunks.
- Retry only appropriate transient failures, using bounded retry policies.
- Keep external API credentials out of logs and manifests.
- Make remote providers explicitly configured rather than silently enabled.

**Acceptance criteria:**
- Tests cover batching, invalid vectors, partial failures, retries, and mapping integrity.
- Missing provider dependencies produce clear errors.
- Embedding configuration is recorded sufficiently to detect incompatibility.

### Step 12 — Indexing

**Purpose:** Persist document records, chunk content, metadata, and embeddings in the configured storage backend.

**Required capabilities:**
- Use existing document-store and vector-store abstractions.
- Support configured adapters such as Qdrant or pgvector where implemented.
- Persist stable document and chunk IDs.
- Store required metadata and source references.
- Create or validate required indexes and collections.
- Support bounded batch writes.

**Important behavior:**
- Avoid duplicate records when the same operation is repeated.
- Detect incompatible index dimensions and schemas.
- Define update and replacement semantics.
- Handle partial batch failures.
- Do not silently delete existing data when creating or rebuilding an index.
- Keep backend-specific dependencies optional.

**Acceptance criteria:**
- Adapter contract tests verify write, read, update, and error behavior.
- Indexing can be retried without unintended duplication.
- The stored records retain the required provenance and metadata.

### Step 13 — Index Verification

**Purpose:** Verify that indexed data matches the intended ingestion output.

**Required checks:**
- Expected document and chunk counts.
- Required records exist.
- Embeddings exist where required.
- Vector dimensions and metadata are compatible.
- Source references and document relationships remain valid.
- Basic retrieval smoke tests succeed where supported.

**Important behavior:**
- Distinguish hard consistency failures from warnings.
- Do not treat successful database writes as proof that the index is correct.
- Handle eventual consistency when the backend requires it.
- Do not claim full index integrity based only on counts.

**Acceptance criteria:**
- Verification detects missing records, vectors, and required metadata.
- A failed verification is visible to the caller.
- Index readiness is reported only after required checks pass.

### Step 14 — Failure Handling

**Purpose:** Recover from transient failures and preserve visibility into permanent failures.

**Required capabilities:**
- Classify transient and permanent errors.
- Use bounded retries with configurable backoff.
- Preserve failure details and source identifiers.
- Support resuming failed work.
- Provide a dead-letter or quarantine mechanism where required by the execution model.
- Report partial pipeline success accurately.

**Important behavior:**
- Never silently lose a document or chunk.
- Do not retry permanent validation errors indefinitely.
- Prevent sensitive document content or secrets from leaking into error logs.
- Make failed items distinguishable from items that have not yet been processed.
- Define behavior for process termination during ingestion.

**Acceptance criteria:**
- Tests simulate parser, embedding, storage, and verification failures.
- Retry exhaustion produces a clear terminal failure.
- Recoverable work can be resumed without duplicating successful writes.

### Step 15 — Idempotency

**Purpose:** Ensure repeated ingestion of the same document does not create unintended duplicates or inconsistent state.

**Required capabilities:**
- Use stable document and chunk identities.
- Track content hashes and processing configuration.
- Make document creation, update, and indexing operations safely repeatable.
- Record completed processing stages where necessary.

**Important behavior:**
- Reprocessing unchanged documents should avoid unnecessary work when safe.
- Changed content must trigger the appropriate downstream work.
- A changed embedding model or chunking configuration must not incorrectly reuse incompatible artifacts.
- Handle concurrent attempts to ingest the same document according to an explicit policy.
- Do not claim exactly-once execution unless the underlying design actually guarantees it.

**Acceptance criteria:**
- Repeated ingestion produces no unintended duplicate records.
- Interrupted and resumed runs converge to a consistent state.
- Changed source content or configuration triggers the appropriate updates.

### Step 16 — Versioning

**Purpose:** Track the versions and configurations that determine ingestion output.

**Required version information:**
- Parser or extraction implementation.
- Normalization configuration.
- Chunking strategy and configuration.
- Embedding model and relevant version information.
- Metadata schema version.
- Index schema or collection version.
- Pipeline configuration version.

**Important behavior:**
- Distinguish source-document versions from processing-configuration versions.
- Detect when an existing index is incompatible with a new configuration.
- Support controlled reprocessing and index rebuilds.
- Preserve the previous usable version until a replacement is verified, where the architecture supports this.
- Document migration and rollback limitations.

**Acceptance criteria:**
- Processing versions are recorded consistently.
- Configuration changes can be detected.
- Rebuild decisions are explainable and testable.

### Step 17 — Observability

**Purpose:** Make ingestion progress, failures, and performance measurable.

**Required capabilities:**
- Structured logs.
- Counters for discovered, accepted, rejected, processed, and failed documents.
- Counts for extracted pages and generated chunks.
- Processing durations and failure rates.
- Embedding and storage latency where measurable.
- Correlation IDs linking a document to its processing stages.
- Clear run summaries.

**Important behavior:**
- Never log API keys, credentials, or full sensitive document content by default.
- Avoid high-cardinality metric labels such as raw document text.
- Keep telemetry optional and separate from core processing logic.
- Distinguish missing measurements from zero-valued measurements.
- Do not claim traces or metrics are available if only logging exists.

**Acceptance criteria:**
- Tests verify important counters and error events.
- A failed run can be diagnosed using structured records.
- Instrumentation does not change ingestion correctness.

### Step 18 — Testing

**Purpose:** Establish confidence that individual stages and the full pipeline work correctly.

**Required test layers:**
- Unit tests for individual components.
- Contract tests for shared interfaces and storage adapters.
- Parser tests using representative documents.
- Chunking and metadata preservation tests.
- Deduplication and idempotency tests.
- Failure and recovery tests.
- Security and hostile-input tests.
- End-to-end ingestion tests.
- Regression tests for previously discovered bugs.

**Important behavior:**
- Use deterministic fixtures and mock external services where appropriate.
- Keep tests independent of live APIs unless explicitly designated as integration tests.
- Do not hide broken behavior by weakening assertions.
- Separate passed, failed, skipped, and blocked tests.
- Make tests for optional integrations conditional on their documented dependencies.

**Acceptance criteria:**
- The full test suite collects without errors.
- Required tests pass in the documented environment.
- Security, failure-handling, and idempotency behavior is covered.
- Test results report actual execution evidence.

### Step 19 — Security

**Purpose:** Prevent unsafe files, unauthorized filesystem access, and untrusted document content from compromising the ingestion process.

**Required capabilities:**
- Validate file types and sizes.
- Enforce source and destination path boundaries.
- Protect against path traversal and unsafe symlinks.
- Treat document content and metadata as untrusted input.
- Validate metadata before persistence.
- Protect credentials and sensitive information.
- Define resource limits for parsing and processing.
- Provide explicit policies for suspicious or malformed documents.

**Important behavior:**
- Never execute document-embedded code.
- Do not treat extracted text as trusted system instructions.
- Prevent a document's metadata from overriding protected system fields.
- Avoid unbounded memory consumption, parsing time, and retries.
- Do not claim prompt-injection prevention from a detector alone.
- Ensure authorization checks are implemented where the surrounding application provides user or tenant boundaries.

**Acceptance criteria:**
- Tests cover malicious filenames, path traversal, malformed files, resource-limit violations, and metadata attacks.
- Failures do not bypass security validation.
- Security checks remain active in the normal ingestion path.

### Step 20 — Lifecycle Management

**Purpose:** Manage document updates, deletion, reprocessing, and cleanup of stale data.

**Required capabilities:**
- Detect changed documents.
- Re-ingest modified content.
- Handle deleted source documents according to an explicit deletion policy.
- Remove or invalidate obsolete chunks and vectors.
- Rebuild affected indexes when required.
- Track lifecycle state and processing history.
- Support safe retries and recovery after interrupted operations.

**Important behavior:**
- Never leave stale content silently retrievable after a confirmed deletion.
- Avoid destructive replacement before the new version is validated.
- Define behavior when source files disappear temporarily or become inaccessible.
- Make deletion operations auditable.
- Use tombstones or equivalent mechanisms if the backend requires them.
- Do not delete shared chunks while they remain referenced by other documents.
- Keep retention and permanent-deletion behavior explicit.

**Acceptance criteria:**
- Tests cover updates, deletions, interrupted replacements, stale vectors, and shared-content references.
- Repeated lifecycle operations remain consistent.
- Failed updates do not silently destroy the last usable version.

## 4. Cross-stage architecture requirements

All 20 stages must work together as one coherent pipeline.

### A. Common contracts

Reuse the project's existing core types and protocols wherever suitable. Introduce new contracts only when necessary.

Define or reuse consistent representations for:
- Source and discovered document.
- Document identity and version.
- Extracted document and extraction result.
- Normalized text.
- Chunk and chunk metadata.
- Embedding result.
- Indexing result.
- Validation result.
- Processing error.
- Pipeline run summary and lifecycle state.

Every object must have a clear contract, validation policy, and documented ownership of its data.

### B. Pipeline orchestration

Provide a clear way to run the complete pipeline and, where appropriate, individual stages.

The orchestration layer must:
- Pass validated outputs between stages.
- Propagate document identity and provenance.
- Stop or quarantine work according to failure policy.
- Track stage status and progress.
- Support resumable processing where the architecture permits.
- Avoid duplicate processing when safely reusable results exist.
- Allow configuration of supported stages without embedding backend-specific behavior in the orchestration layer.

Do not introduce a large workflow framework merely for the sake of abstraction.

### C. Configuration

Use the project's existing configuration architecture.

Configuration must cover relevant file limits, supported formats, chunking, embedding, storage, retries, concurrency, security, and observability.

Validate configuration before processing begins. Provide safe defaults where appropriate, document optional settings, and reject invalid combinations early.

Keep secrets out of source control, manifests, generated documentation, and logs.

### D. Dependencies

Keep the core pipeline and shared contracts lightweight.

Declare optional dependencies for parser libraries, OCR, embedding providers, and storage adapters. Missing optional dependencies must produce actionable messages.

Do not silently install packages or contact external APIs. Network-connected providers must require explicit configuration.

### E. Framework independence

Keep the core ingestion contracts framework-neutral. Do not make LangChain or LlamaIndex mandatory dependencies unless the existing specification explicitly requires them.

Adapters may integrate with external frameworks, but they must not leak framework-specific objects into the core contracts unnecessarily.

## 5. End-to-end acceptance criteria

V2 ingestion is acceptable only when the following are demonstrated:

1. A supported document can be discovered, validated, identified, loaded, extracted, normalized, enriched, chunked, validated, deduplicated, embedded, indexed, and verified.
2. A corrupt or unsupported document is rejected with a clear reason.
3. A document with partial extraction failures reports those failures accurately.
4. Re-ingesting an unchanged document does not create unintended duplicates.
5. Modifying a document triggers the appropriate reprocessing.
6. Changing embedding or chunking configuration does not silently reuse incompatible artifacts.
7. Transient provider or storage failures are retried within configured limits.
8. Permanent failures are recorded and recoverable where supported.
9. An interrupted run can resume without inconsistent duplicate state.
10. Deleted documents do not remain silently retrievable after lifecycle processing succeeds.
11. Chunk metadata and citation provenance survive the complete pipeline.
12. Index verification detects missing records and incompatible vectors.
13. Security validation cannot be bypassed through an ordinary ingestion path.
14. Observability provides a useful run summary without exposing sensitive content.
15. Unit, integration, security, and regression tests cover the implemented behavior.
16. Documentation describes actual capabilities, dependencies, limitations, and configuration.
17. Existing library components continue to work, or any necessary breaking changes are explicitly documented and tested.

Do not claim all 20 steps are complete merely because a basic end-to-end happy path works.

## 6. Deliverables

Produce:

- Implemented V2 ingestion components and integration changes.
- Updated or new shared contracts where required.
- Component manifests and dependency declarations.
- Unit, contract, integration, security, and regression tests.
- Representative fixtures that do not contain sensitive data.
- Updated README and component documentation.
- An architecture document showing the 20 stages and their dependencies.
- Configuration examples with no real secrets.
- A gap-analysis report showing what existed, what was added, and what remains blocked.
- A verification report containing commands actually executed and their results.

## 7. Final execution rules

1. Inspect before implementing.
2. Reuse correct existing functionality.
3. Implement missing and incomplete behavior rather than duplicating components.
4. Do not create fake placeholders to satisfy acceptance criteria.
5. Do not silently weaken requirements or tests.
6. Do not claim support for an external service or file format without working implementation and verification.
7. Preserve backward compatibility where practical and document unavoidable changes.
8. Keep changes focused on ingestion V2.
9. Do not commit, push, publish, or perform unrelated destructive operations.
10. At completion, report each of the 20 steps as complete, partial, missing, or blocked, supported by actual evidence.

**Final objective:** deliver a reliable, maintainable, testable ingestion pipeline that can be reused in real RAG applications, with clear failure behavior and trustworthy document provenance.
